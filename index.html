CVE-2011-2523 / BID 48539 ｜ Kali + Metasploitable2

一、要验证什么

vsftpd 2.3.4 的 str.c 里有一行与程序功能无关的代码，只看用户名里有没有 :（0x3a）和 )（0x29）；P10 说命中后 6200 端口绑定 /bin/sh，且是 root 权限；PoC 证明存在即可，6200 开放就到头。

用 curl 亲手拆开一次 HTTP 请求

《主动扫描》课后实践。

一、目的

ch4 讲了 nmap、dirb、whatweb 这几个工具，它们底层干的是同一件事——发一个请求，看对方怎么回。curl 就是我亲手去干这件事：请求方法、请求头、请求体，全都由我自己写。

这次我想验证一个具体的问题：能不能用 curl 手工复现一次 whatweb 那种「网站指纹识别」。

二、环境

  • 攻击机：Kali Linux（VMware 虚拟机，内网 IP 192.168.64.4）
  • 目标：www.baidu.com 与 httpbin.org 两个公开站点
  • curl 版本：8.20.0

本次所有请求都只针对公开网站和公开测试接口，没有对任何未授权的系统发起过测试。

图 1 curl –version

三、六个练习

3.1 抓网页源码：curl 拿到的是什么

图 2 抓取网页源码

结论：curl 拿到的是原始响应体，浏览器是在这堆字符之上再做解析、执行脚本、渲染成页面的。平时我们看网页，看到的是「渲染后的结果」；curl 让我看到了网页的源码。

这也解释了一个现象——同一张网页，右键「查看源代码」和浏览器里看到的差别很大，正是因为前者才是服务器真正发过来的东西。

3.2 只看响应头：这一步和 whatweb 是同一件事

图 3 只看响应头

这段输出里有两处值得说。

第一，Server 头只回了 bfe，没有版本号。我查到的常见示例是 bfe/1.0.8.18 这种带版本的写法，而我这里只有 bfe。bfe 是百度自研的接入层，不返回版本号不是它「坏了」，而是有意隐藏——不告诉外面自己跑的是哪一版，别人就没法照着版本号去找对应的已知漏洞。反过来，一个站点 Server 头带完整版本号，说明运维没做过基础加固。Server 头是服务器自己写的，可以随便改，所以真正做评估时不能只靠这一个头，要看一排特征一起对。

第二，Content-Length: 0 并不代表页面是空的。因为 -I 发的是 HEAD 请求，只要求响应头、不要正文，长度当然是 0。想看真正的正文大小，就得不带 -I。

结论：curl -I 手工看 Server 头，和 whatweb 自动识别网站指纹，是同一个思路，只是一手动、一自动。

3.3 看完整握手：一个参数看穿 HTTP 报文结构

这里踩了个坑，问题出在 Linux 的一个基础机制：程序其实有两个输出口，而管道 | 只接管其中一个（1 号口）。2 号口不经过管道处理，直接送到屏幕上。curl -v 就是这样分流的：网页正文走 1 号口，* Trying...、> GET /、< HTTP/1.1 200 这些调试信息全部走 2 号口。这样一来，你想看的（前 60 行里带 > 和 < 的那部分）被 head 截掉了，你不想看的（几百行 * TLSv1.2）全都刷在屏幕上。必须写 2>&1 把错误流合并进标准输出，head 才拦得住。

输出里以 * 开头的是 curl 自己的调试信息，> 是我发出去的请求头，< 是对方回的响应头。

图 4 完整握手过程（上）

图 4 完整握手过程（下）

第一，先撞 IPv6 再回退 IPv4。 日志里先出现 Immediate connect fail for 2408:... : Network is unreachable，连着两条，然后才 Trying 157.148.69.151:443。原因是我的 Kali 没配 IPv6，curl 按顺序先试 IPv6，直接不通，再回退到 IPv4 才连上。

第二，TLS 1.3 发起，最后协商成 1.2。 日志里先是 TLSv1.3 (OUT), TLS handshake, Client hello，也就是我的客户端支持并优先尝试 TLS 1.3；但往下看会发现 TLSv1.2 (IN), TLS handshake, Certificate，最后一行 SSL connection using TLSv1.2 / ECDHE-RSA-AES128-GCM-SHA256。这是 TLS 的正常机制：双向协商，取双方都支持的最高版本。顺带还读到了证书信息。

第三，一条连接的四元组。 最后有 Established connection to www.baidu.com (157.148.69.151 port 443) from 192.168.64.4 port 36246。目标 IP 加 443 端口，源 IP 是我这台 Kali 随机分配的高端口。说到底，扫描器要探的就是这个「IP + 端口」，其余都是在这条连接上做的事。

程序的两个出口：

编号 名字 是什么 默认去向
0 stdin 标准输入 你喂给程序的东西 键盘
1 stdout 标准输出 程序的正常结果 屏幕
2 stderr 标准错误 报错信息和调试信息 屏幕

图 5 下载并核对文件

-o（小写）是自己起名字，-O（大写）是沿用对方 URL 里的文件名。ls -lh 证明文件真的落到了磁盘上。

3.5 带参数发 GET

图 6 带参数 GET 请求

返回的 JSON 里，args 字段把两个参数原样回显了，method 是 GET，url 里也能看到完整参数。

3.6 POST 与伪装 User-Agent

返回的 JSON 里能看到这两行：

-d 会自动把请求方法改成 POST，并补上 Content-Type: application/x-www-form-urlencoded。返回里的 form 字段说明服务端确实收到了这两个字段。

然后是伪装 UA。

图 7 伪装 User-Agent 的请求头证据

这条 > User-Agent 才是真的证据：请求头确实从默认的 curl/8.20.0 变成了浏览器的 UA。

默认的 curl/8.20.0 一眼就能看出「这不是浏览器」。有些站点会按 UA 判断来访者，看到 curl 就直接拒绝，或者返回一个假页面糊弄你。扫描器伪装 UA 就是为了不被这么挡在门外——这也是后面学各种「绕过」的起点。UA 是客户端单方面声明的信息，服务端无法验证。

四、做完之后的总结

工具 它其实在干什么
whatweb 反复发请求，比对 Server、X-Powered-By 等响应头，猜对方是什么
dirb 拿字典拼 URL，一条条发 GET，看哪个回 200 而不是 404
curl 上面两个工具的地基——一个请求，由你自己发

问：curl -I 和 curl -v 都能看到服务端信息，什么时候用哪个？

答：想要一个干净结论时用 -I。我这次只想知道「对方是什么服务器、返回什么状态码」。想知道「这一路到底发生了什么」才用 -v——它把 DNS 解析、IPv6 撞墙、TLS 握手版本、证书链、甚至源端口都打出来。因此使用：-I 用来快速探路，-v 用来查问题和写记录。

附：本文所有命令均在自己可控的环境中对公开站点执行，未针对任何第三方系统做未授权测试。

四、小结

被动扫描的核心是”知己知彼”：通过 ZoomEye、Shodan 等测绘引擎与证书日志等公开渠道，在不接触目标的情况下即可勾勒出目标的资产轮廓（域名、子域名、开放服务、设备类型），这些信息既是安全排查的起点，也可能被攻击者利用进行社会工程学攻击——如课件中的摄像头案例，不少设备使用默认口令，被测绘引擎收录后存在被陌生人”围观”的风险。对防守方而言，主动梳理自己的公网资产、清理默认口令，同样是被动信息收集视角下的必修课。

QQ 流量分析

目标：在自己的电脑上，用 Wireshark 看清楚 QQ 到底在干什么——它连哪个端口、平时的心跳长什么样、发一条消息之后网络里多出了什么，以及同一个 WiFi 下发一张图片时，数据究竟走了哪条路。

整个过程分两段：先只观察，靠端口和包长定位；再动手，把局域网里传的那张图从抓包文件里原样导出来。下面按实际做的顺序记一遍。

一、先定位 QQ 用哪几个端口

第一步不是开 Wireshark，而是先知道该过滤什么。QQ.exe 会同时开一堆进程，但只有主进程在跑业务，所以先按内存占用挑出它：

六七个 QQ.exe 里，33316 占了 159 MB，其余几个只有几 MB 到几十 MB，主进程就是它。

拿到 PID 再查它连了谁：

这一步只能查到「跟腾讯服务器会话」的端口。想看全，就把所有已建立的连接列出来：

一屏几十行里，本地回环、443、11111 这些都不相关，只有红框那行是真正的业务连接：

这里有一个后面还会踩到的区别：58394 是本机临时端口，重开一次 QQ 就换一个；14000 是服务器端口，相对固定。所以过滤器写 tcp.port == 14000 是可靠的，写本地端口则不保证下次还对得上。

二、抓心跳：包长是唯一的线索

Wireshark 里过滤 tcp.port == 14000，先采一段「只挂着、不发任何消息」的基线。

整段记录里出现过的帧长只有 74 / 154 / 227 三种，大约每 10 秒一轮，反复出现「227 → 154 → 74」这个组合。这就是心跳：服务器推一下、客户端回一个、再补一个 ACK。

然后发一条消息，再抓一次：

多出来的三种长度是 370 / 798 / 994，同样是「服务器 → 我 → 服务器」的三段式。

帧长不能直接当内容长度用，中间隔着协议头：

帧长 内容长度 含义
370 296 服务器推给我的东西
798 724 我发出去的消息
994 920 服务器给我的回执

换算关系是：

也就是说，去掉 74 字节的固定开销，剩下的才是真正的应用层数据。这也解释了为什么基线里没有 370 以上的包——不发消息就没有大块内容。

三、双击 798 那行，看里面是什么

点开之后，协议栈一路展开到 TCP 的 Data (724 bytes)，下面那块就是原始的十六进制 + ASCII 对照。往下翻到偏移 00b0 附近，ASCII 那一栏里能直接读出数字。

结论是：包长能告诉你「有没有发东西、发了多大」，而载荷的这一段是明文的。对于只想知道「发没发消息、消息多长」这件事，加密与否都不影响——长度本身就是一种信息。

四、发图片：端口全变了

接下来是发图片。同样的流程重来一遍，先拿 PID，再查端口：

结果是什么都查不到。原因很明确：局域网直连只在传文件的那十几秒存在，等你想起来去 netstat，连接已经断了。所以这次不能靠「先找端口再抓包」。

换一个思路：先抓全量，抓完再按字节数排队找端口。

Wireshark 里点三下：

  1. 菜单「统计」→「会话」（Statistics → Conversations）
  2. 切到 TCP 标签页
  3. 点 Bytes 列表头，让它从大到小排

排在第一行的就是答案：10.43.58.211:55327 ↔ 10.43.58.52:8082，71 万字节，占这次抓包总量的 100%。端口是 8082。

这个办法的好处是不依赖猜端口——端口号会变，不知道端口，就先按体积排，先找体积最大的。

五、看清 8082 上发生了什么

过滤器填上 tcp.port == 8082，回到包列表。

从第 164 行开始：电脑（10.43.58.211）向 8082 发起三次握手（SYN → SYN,ACK → ACK），握完手第 167 行立刻是一条 HTTP GET /qqline/...。

也就是说，是电脑在向手机「要」一个文件，而不是手机推过来。手机的回答是：

HTTP/1.1 200 OK (JPEG JFIF image)，明说了返回的是一个 JPEG 图片。

双击这一行看细节：

两个关键信息：

  • [Full request URI: http://10.43.58.52:8082/qqline/...] —— 这是一个明文 HTTP 请求，地址是内网 IP，不是 https。
  • File Data: 708970 bytes，下面从 FF D8 FF E0 开始——这是 JPEG 的标准文件头。

到这一步结论已经很清楚了：这段通信没有任何加密。

六、把图片从抓包里捞出来

过滤器里保留 tcp.port == 8082，敲回车，然后点菜单栏「文件」→「导出对象」→「HTTP…」。

对象列表里一眼能认出它：353 行，708 KB，主机名是 10.43.58.52:8082，文件名就是那串 r2MFvA57L2d3dF+8wK57nY7CUmkP1kaheAV9xEUykcNa25FbGt...。

选中那一行，点「保存」，文件名手动填成 图片.jpg，双击就能直接打开看——图片完整恢复了。

到这里，「能不能还原」这个问题有了答案：能，而且是原图，708,970 字节一个不少。

八、结论

同一份数据，存在两条完全不同的传输路径：跨公网时走腾讯服务器的加密通道，抓包里只能观测到包长与心跳；而在同一局域网内，QQ 客户端会降级为明文 HTTP 直连（端口 8082），可以完整还原传输的 JPEG 原图（708,970 字节）。

这说明「能不能还原」取决于路径选择，而不是某一个协议本身的安全强度。加密做得很好的通道，也可能在特定条件下被换成一条完全裸奔的捷径。

以上抓的都是自己电脑和自己手机的流量。

网络安全意识

等保2.0：从“系统安全”到“安全生态”

大一学期学《信息安全导论》的时候，老师提过“等保”，当时只记住了“三级等保”这个词，具体是什么、为什么重要，脑子里其实一片模糊。这学期开始接触网络安全法和一些合规相关的内容，才慢慢把等保2.0的轮廓拼出来。它不只是一份技术标准，更像是一套关于“如何在现实世界里把安全责任落地”的制度设计。

等保1.0的时代背景和现在差别很大。1994年的《计算机信息系统安全保护条例》确立等级保护制度的时候，互联网还没有渗透到生活的每个角落，保护对象基本就是单位内部的信息系统。1.0版本的核心逻辑是“分级别、分等级地保护”，思路本身没有问题，但它默认了一个前提：你要保护的东西是一台台相对独立的机器或系统。这个前提在云计算、移动办公和物联网设备铺开之后就不太成立了。一台服务器可能同时承载好几个租户的业务，一个传感器可能连着生产网也连着办公网，传统的边界防护模型很难描述清楚“边界到底在哪里”。等保2.0在2019年发布，很大程度上就是在回应这种“旧框架装不下新现实”的困境。

保护对象的扩展是我觉得最直观的变化。1.0主要盯着传统信息系统，2.0把云计算平台、物联网系统、工业控制系统、移动互联系统统统纳入保护范围。这意味着一个用公有云部署业务的公司，不能只按通用要求做一遍就完事，还得看云计算扩展要求里关于虚拟化安全、镜像保护、云服务商选择这些条款。同样，一个工厂里的工控系统，如果按传统IT系统的安全要求去套，很多控制点根本对不上——工控环境对实时性和可用性的要求，跟一般业务系统完全不是一回事，所以才需要单独的扩展要求。

安全框架的调整也值得琢磨。1.0的技术要求分成物理安全、网络安全、主机安全、应用安全和数据安全五块，每一块相对独立。2.0换成了“一个中心、三重防护”：安全管理中心管集中管控，三重防护分别是安全通信网络、安全区域边界和安全计算环境。这个变化不只是换了几个章节名字。原来的“网络安全”被拆成了通信网络和区域边界，这意味着传输过程中的保密性和完整性被单独拎出来强调，边界上也不只是访问控制，入侵防范、恶意代码防范和安全审计都变成了硬性要求。而安全管理中心这个概念，在1.0里是没有的。它要求把系统管理、审计管理、安全管理和集中管控整合到一个统一的平台上，换句话说，安全不能再是各个设备各自为战，得有一个人在楼上看着全局。

可信验证是2.0里另一个让我觉得有意思的点。1.0基本没有可信计算的要求，2.0从第一级到第四级都加了“可信验证”控制点。最低一级的要求是基于可信根对系统引导程序、系统程序做验证，检测到完整性被破坏要报警。到了更高级别，验证的范围会扩展到应用程序的关键执行环节，还要形成审计记录上报。这背后的思路其实很清楚：与其等恶意代码跑起来再去杀，不如在它还没机会执行的时候就发现系统已经不可信了。

跟等保1.0相比，2.0还多了一层法律上的“牙齿”。《网络安全法》第二十一条把等级保护制度写成了网络运营者的法定义务，不履行的话，轻则警告责令改正，重则罚款，直接负责的主管人员也可能被追责。我看到的案例里，有公司因为没做等保、系统被攻击导致数据泄露，被公安机关行政处罚的。以前等保可能更多被当成“合规检查要过的那一关”，现在它和法律责任直接挂钩，性质就不一样了。

站在学生的角度，我其实更关心的是：等保2.0在纸面上写得挺完整，落地的时候到底会卡在哪。看了几篇企业合规的实践文章，发现比较常见的坑是云环境下的责任划分——云服务商和云租户各自要承担哪些安全义务，很多时候双方的理解并不一致，需要通过责任共担模型来明确。另一个问题是“测评过了就放松”，安全运营的持续性投入跟不上，等到复测的时候又冒出一堆不符合项。这些问题说明，等保2.0的标准本身虽然已经比较细致了，但它能不能真正起作用，取决于组织有没有把安全当成日常的事，而不是三年一次的考试。

接下来我要学的东西还很多，密码学、网络攻防、安全测评这些课都会碰到和等保相关的内容。现在我对它的理解还比较浅显，但至少有一点是清楚的：等保2.0试图回答的不是“用什么设备防什么攻击”这种单点问题，而是一个更麻烦的问题——在一个技术形态不断变化的环境里，怎么让不同规模、不同行业的组织都有一套可以参照的安全底线。这个底线能不能守住，既取决于标准写得好不好，也取决于每一个具体的人有没有认真对待它。
