目标：在自己的电脑上，用 Wireshark 看清楚 QQ 到底在干什么——它连哪个端口、平时的心跳长什么样、发一条消息之后网络里多出了什么，以及同一个 WiFi 下发一张图片时，数据究竟走了哪条路。

整个过程分两段：先只观察，靠端口和包长定位；再动手，把局域网里传的那张图从抓包文件里原样导出来。下面按实际做的顺序记一遍。

## 一、先定位 QQ 用哪几个端口

第一步不是开 Wireshark，而是先知道该过滤什么。QQ.exe 会同时开一堆进程，但只有主进程在跑业务，所以先按内存占用挑出它：

```powershell
tasklist /FI "IMAGENAME eq QQ.exe"
```

{% asset_img 01-tasklist-pid.jpeg tasklist 查看 QQ.exe 进程，内存占用最大的是 33316 %}

六七个 QQ.exe 里，33316 占了 159 MB，其余几个只有几 MB 到几十 MB，主进程就是它。

拿到 PID 再查它连了谁：

```powershell
netstat -ano | findstr "33316"
```

这一步只能查到「跟腾讯服务器会话」的端口。想看全，就把所有已建立的连接列出来：

```powershell
netstat -ano | findstr "ESTABLISHED"
```

{% asset_img 02-netstat-established.jpeg netstat -ano 过滤 ESTABLISHED，红框那行才是 QQ 主进程连外网的连接 %}

一屏几十行里，本地回环、443、11111 这些都不相关，只有红框那行是真正的业务连接：

```
TCP  [2408:845d:3b51:b736:fc02:...:d076]:58394  [2409:8c54:871:2::24]:14000  ESTABLISHED  33316
     └──────── 你这台电脑 ────────┘              └──── 腾讯服务器 ─┘                    PID
     :58394                                        :14000
     （本机临时端口，每次重开 QQ 都会变）            （服务器端口）
```

这里有一个后面还会踩到的区别：**58394 是本机临时端口，重开一次 QQ 就换一个；14000 是服务器端口，相对固定**。所以过滤器写 `tcp.port == 14000` 是可靠的，写本地端口则不保证下次还对得上。

## 二、抓心跳：包长是唯一的线索

Wireshark 里过滤 `tcp.port == 14000`，先采一段「只挂着、不发任何消息」的基线。

{% asset_img 03-baseline-heartbeat.jpeg 基线抓包，帧长只有 74 / 154 / 227 三种 %}

整段记录里出现过的帧长只有 **74 / 154 / 227** 三种，大约每 10 秒一轮，反复出现「227 → 154 → 74」这个组合。这就是心跳：服务器推一下、客户端回一个、再补一个 ACK。

然后发一条消息，再抓一次：

{% asset_img 04-after-message.jpeg 发消息之后，多出了 370 / 798 / 994 三种长度 %}

多出来的三种长度是 **370 / 798 / 994**，同样是「服务器 → 我 → 服务器」的三段式。

帧长不能直接当内容长度用，中间隔着协议头：

| 帧长  | 内容长度 | 含义        |
| --- | ---- | --------- |
| 370 | 296  | 服务器推给我的东西 |
| 798 | 724  | 我发出去的消息   |
| 994 | 920  | 服务器给我的回执  |

换算关系是：

```
帧长 = 74 + 内容长度
74 = 14（以太网头）+ 40（IPv6 头）+ 20（TCP 头）
```

也就是说，去掉 74 字节的固定开销，剩下的才是真正的应用层数据。这也解释了为什么基线里没有 370 以上的包——不发消息就没有大块内容。

## 三、双击 798 那行，看里面是什么

{% asset_img 05-packet-798-detail.jpeg 双击 798 字节那条包，TCP 载荷的十六进制与 ASCII 双栏对照 %}

点开之后，协议栈一路展开到 TCP 的 `Data (724 bytes)`，下面那块就是原始的十六进制 + ASCII 对照。往下翻到**偏移 00b0 附近**，ASCII 那一栏里能直接读出数字。

结论是：包长能告诉你「有没有发东西、发了多大」，而载荷的这一段是明文的。对于只想知道「发没发消息、消息多长」这件事，加密与否都不影响——长度本身就是一种信息。

## 四、发图片：端口全变了

接下来是发图片。同样的流程重来一遍，先拿 PID，再查端口：

```powershell
tasklist /FI "IMAGENAME eq QQ.exe"
netstat -ano | findstr "19696"
```

结果是什么都查不到。原因很明确：**局域网直连只在传文件的那十几秒存在**，等你想起来去 netstat，连接已经断了。所以这次不能靠「先找端口再抓包」。

换一个思路：先抓全量，抓完再按字节数排队找端口。

Wireshark 里点三下：

1. 菜单「统计」→「会话」（Statistics → Conversations）
2. 切到 **TCP** 标签页
3. 点 **Bytes** 列表头，让它从大到小排

{% asset_img 06-conversations-bytes.png 会话统计里按 Bytes 排序，第一行就是传图片的会话 %}

排在第一行的就是答案：`10.43.58.211:55327 ↔ 10.43.58.52:8082`，71 万字节，占这次抓包总量的 100%。**端口是 8082**。

这个办法的好处是不依赖猜端口——**端口号会变，不知道端口，就先按体积排，先找体积最大的**。

## 五、看清 8082 上发生了什么

过滤器填上 `tcp.port == 8082`，回到包列表。

{% asset_img 07-tcp-8082-get.jpeg 8082 端口上，电脑向手机发起三次握手，接着就是一条 HTTP GET %}

从第 164 行开始：电脑（10.43.58.211）向 8082 发起三次握手（SYN → SYN,ACK → ACK），握完手第 167 行立刻是一条 **HTTP GET `/qqline/...`**。

也就是说，是**电脑在向手机「要」一个文件**，而不是手机推过来。手机的回答是：

{% asset_img 08-http-200-jpeg.jpeg 手机返回 200 OK，内容类型 JPEG JFIF image %}

`HTTP/1.1 200 OK (JPEG JFIF image)`，明说了返回的是一个 JPEG 图片。

双击这一行看细节：

{% asset_img 09-jpeg-file-data.jpeg 请求行、完整 URL，以及 File Data: 708970 bytes %}

两个关键信息：

- `[Full request URI: http://10.43.58.52:8082/qqline/...]` —— 这是一个**明文 HTTP 请求**，地址是内网 IP，不是 https。
- `File Data: 708970 bytes`，下面从 `FF D8 FF E0` 开始——这是 JPEG 的标准文件头。

到这一步结论已经很清楚了：这段通信没有任何加密。

## 六、把图片从抓包里捞出来

过滤器里保留 `tcp.port == 8082`，敲回车，然后点菜单栏「文件」→「导出对象」→「HTTP...」。

{% asset_img 10-export-objects.jpeg HTTP 对象列表，353 行 708 KB 就是那张图 %}

对象列表里一眼能认出它：353 行，708 KB，主机名是 `10.43.58.52:8082`，文件名就是那串 `r2MFvA57L2d3dF+8wK57nY7CUmkP1kaheAV9xEUykcNa25FbGt...`。

选中那一行，点「保存」，**文件名手动填成 `图片.jpg`**，双击就能直接打开看——图片完整恢复了。

到这里，「能不能还原」这个问题有了答案：能，而且是**原图**，708,970 字节一个不少。

## 七、数据到底走了哪条路

把时间轴对齐之后，整个过程是这样的：

{% asset_img 11-timeline.png 从 +10.80s 到 +10.90s 的四个动作，以及各自走的路径 %}

关键点在于：**服务器只负责「通知」和「记录回执」**（就是那 448 和 852 字节），图片本身完全没经过服务器，是手机和电脑之间直接传的。

方向也值得注意。抓包里是**电脑主动发 GET（当客户端），手机在 8082 上等着被取（当服务器）**。所以链路是：

```
服务器通知电脑 → 电脑去向手机 GET → 手机被取走文件
```

而两个方向并不对称：

| 方向      | 是否通 | 原因              |
| ------- | --- | --------------- |
| 手机 → 电脑 | 被拦  | 要穿过 Windows 防火墙 |
| 电脑 → 手机 | 通   | 手机是热点网关         |

{% asset_img 12-two-paths.png 同一张图的两种传法：跨公网走加密通道，同局域网走明文 HTTP %}

## 八、结论

同一份数据，存在两条完全不同的传输路径：跨公网时走腾讯服务器的加密通道，抓包里只能观测到包长与心跳；而在同一局域网内，QQ 客户端会**降级为明文 HTTP 直连**（端口 8082），可以完整还原传输的 JPEG 原图（708,970 字节）。

这说明「能不能还原」取决于**路径选择**，而不是某一个协议本身的安全强度。加密做得很好的通道，也可能在特定条件下被换成一条完全裸奔的捷径。

---

以上抓的都是自己电脑和自己手机的流量。
